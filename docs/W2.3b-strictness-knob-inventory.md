## 1. The override mechanism (how a template sets a knob)

The engine builds the `options` object each module's `execute(input, options, tools)`
receives by spreading the template/run options over the manifest defaults:

```js
// content-pipeline-v2--news-production/server/workers/stageWorker.js:491
const options = { ...(manifest.options_defaults || {}), ...(entityRun.options || {}) };
```

Consequences:

- **Every manifest option is template-overridable by default.** `entityRun.options`
  (sourced from `submodule_runs.options`, populated from the template's execution
  plan when the run is created) wins over `options_defaults`.
- **Locking a knob = removing it from `options`.** W2.3 did exactly this for the
  fact-check `prompt`: it inlined `MANIFEST_DEFAULT_PROMPT` in `execute.js` and
  dropped `prompt` from the manifest. Any `prompt` a template supplies still lands
  in `otherOptions` — and is ignored (`execute.js:293-295`). That is the template
  for every lock recommended below.
- **Current usage is latent, not active.** Across all 36 prod templates, **zero**
  set any QA option in their `execution_plan` (`grep -c expected_checks|pass_threshold|
  no_sources_behavior|min_sections` over `templates.execution_plan` = 0). Every
  checker runs at its manifest default today. The risk this document addresses is
  the *mechanism* (a template can weaken a checker invisibly), not present-day
  weakening. (`routing_rules` / `failure_thresholds` / `escalation_rules` seen in
  some plans are a separate card-based engine routing layer, not loop-router
  module options — out of scope here.)

## 2. The governing rule (Daniel; binding)

1. **Prompts and verdict logic are LOCKED.** No template may rewrite them.
2. **Numeric thresholds MAY remain template-tunable — but only where a specific
   reason is written down.** A threshold with no documented rationale gets locked.
3. **Rationale.** A threshold is visible in the run record, so a weakened one leaves
   a trace. Rewritten verdict logic is invisible — a weakened checker emits the same
   artifact with a green tick on it.

**The classification test is NOT "numeric vs behavioural."** It is:

> *Can this knob make the checker certify something it did not actually verify, and
> would that survive into the pass/fail signal the router acts on (`qa_pass`) without
> leaving a trace?* If yes → **lock** (it is verdict logic). If it only tightens/loosens
> a bar whose value is recorded in the run → **numeric threshold**, keep tunable only
> with a written reason. If it is a per-format spec that changes *what this content
> type is*, not *whether the checker did its job* → it stays tunable, documented.

This is why (below) `require_faq` stays tunable but `require_at_least_one_citation`
locks: the first says "this format has no FAQ" (recorded, honest); the second
switches off the citation checker's reason to exist and still emits green.

Verdicts used below: **LOCK** (remove from options, hardcode) · **NARROW** (stays
tunable but floored/bounded and requires a written rationale) · **SURVIVE** (stays
freely tunable; reason already written or not a weakening vector) · **LOCKED ✓**
(already hardcoded, no change).

## 3. Inventory

### 3.1 hallucination-detector (`step-6-qa/hallucination-detector`)

| Knob | Controls pass/fail via | Template-set? | Default | Kind | Verdict |
|---|---|---|---|---|---|
| `prompt` (fact-check) | the entire verification | **No** — inlined W2.3, override ignored | `MANIFEST_DEFAULT_PROMPT` | verdict logic | **LOCKED ✓** |
| `no_sources_behavior` | zero-source branch: `fail`/`flag`/`pass` | Yes | `fail` | behavioural / verdict logic | **LOCK** |
| `allow_empty_content` | no-`content_markdown` branch: skip-with-pass when `true` | Yes | `false` | behavioural / verdict logic | **LOCK** |
| `flag_zero_claims_over_chars` | char cutoff: substantial-zero-claim **fail** vs short-zero-claim soft-pass | Yes | `500` | numeric threshold | **SURVIVE** |
| `pass_threshold` | `hallucination_score >= threshold` ⇒ `qa_pass` | Yes | `0.9` | numeric threshold | **NARROW** |
| `max_source_chars` | source text truncated into LLM context | Yes | `100000` | numeric (operational) | **SURVIVE** |
| `claims_per_batch` | claims per LLM call | Yes | `10` | operational | **SURVIVE** |
| `ai_model` / `ai_provider` | which model verifies | Yes | `sonnet`/`anthropic` | operational | out of scope¹ |

- **`no_sources_behavior` → LOCK.** This is verdict logic, and the dangerous kind.
  `pass` restores the **exact** H20 bug (claimful content, zero sources ⇒
  `qa_pass:true, score:1`). `flag` is nearly as bad through the router: it sets
  `qa_pass:true` and the router reads only `qa_pass` (it never inspects
  `needs_review`), so a flagged entity routes as a pass — the `needs_review` trace
  lives only in the item detail, not the signal the router acts on. Hardcode `fail`.
  A pipeline that legitimately has no sources should express that by **not scheduling
  the hallucination-detector** (visible in the execution plan) — not by softening the
  verdict per template (invisible).
- **`allow_empty_content` → LOCK.** Same class: `true` certifies absent content as a
  pass. A template with legitimately no content should not schedule the checker.
- **`flag_zero_claims_over_chars` → SURVIVE.** *This is the one knob that genuinely
  stays freely tunable.* It has a written rationale already, in both code and manifest:
  "Calibration knob: measure the trip rate; do not dial down to silence a genuine
  halt." It is a true calibration parameter (the H21 padding-blind cutoff is
  empirical — it must be tuned against the real false-positive rate on live content),
  a weakened value is recorded in the run (`config_overrides`), and it can only be
  wrong in a way that leaves a trace. Keep it. (Optional hardening: cap `max` below
  `100000` so it cannot be pushed high enough to disable the substantial-content fail
  entirely — the ceiling, not the knob, is the risk.)
- **`pass_threshold` → NARROW.** Legitimately varies by content type, but currently
  `min: 0.0`, so a template could set `0` and pass everything (the score is still
  recorded, so it leaves a trace — hence NARROW, not LOCK). Recommendation: keep
  tunable, add a floor (e.g. `min: 0.5`, or the per-checker floor tracked as the
  BACKLOG "#50 severity floor"), and require the template to record a one-line reason
  when it overrides the default.
- **`max_source_chars` / `claims_per_batch` → SURVIVE (operational).** Neither can
  manufacture a false green: truncating source only *starves* the verifier (more
  `unsupported`, i.e. stricter). They tune cost/context, not the verdict direction.

¹ `ai_model`/`ai_provider` can weaken the check by selecting a weak verifier, but that
is model-governance, a different control surface than thresholds or verdict logic.
Residual risk; flagged, not classified here.

### 3.2 citation-coverage-checker (`step-6-qa/citation-coverage-checker`)

| Knob | Controls pass/fail via | Template-set? | Default | Kind | Verdict |
|---|---|---|---|---|---|
| `require_at_least_one_citation` | zero-citation ⇒ auto-fail (toggle) | Yes | `true` | behavioural / verdict logic | **LOCK** |
| `require_factual_citations` | flag uncited factual claims (toggle) | Yes | `true` | behavioural / verdict logic | **LOCK** |
| `pass_threshold` | `citation_score >= threshold` ⇒ `qa_pass` | Yes | `0.7` | numeric threshold | **NARROW** |
| `verify_urls` | HEAD-check source URLs | Yes | `false` | behavioural — **report-only** | **SURVIVE** |

- **`require_at_least_one_citation` → LOCK.** `false` lets content with zero `[#n]`
  citations skip the auto-fail and score its way to a pass — switching off the
  citation checker's core assertion, invisibly. Hardcode `true`.
- **`require_factual_citations` → LOCK.** `false` stops flagging uncited factual
  claims, so `problemCount` drops and the score inflates toward a pass. Same class.
  Hardcode `true`.
- **`pass_threshold` → NARROW.** As §3.1: floor + documented rationale. `min: 0.0`
  today.
- **`verify_urls` → SURVIVE (report-only).** Dead URLs are computed and printed
  (`dead_urls_text`) but **never feed `citation_score` or `qa_pass`** — so this knob
  does not affect the verdict and is out of the lock scope. *Latent defect worth a
  BACKLOG item (not fixed here): a dead source URL should arguably fail the citation
  gate; today it is cosmetic.*

### 3.3 qa-structural (`step-6-qa/qa-structural`)

| Knob | Controls pass/fail via | Template-set? | Default | Kind | Verdict |
|---|---|---|---|---|---|
| taxonomy-marker / dup-token force-fail | force `qa_pass:false`, outside score ratio | **No** — hardcoded | — | verdict logic | **LOCKED ✓** |
| `pass_threshold` | `structural_score >= threshold` ⇒ `qa_pass` | Yes | `0.8` | numeric threshold | **NARROW** |
| `min_sections` | H2-section-count check | Yes | `5` | numeric (format spec) | **NARROW** |
| `min_words_per_section` | thin-section check | Yes | `100` | numeric (format spec) | **NARROW** |
| `min_total_words` | total-word-count check | Yes | `1500` | numeric (format spec) | **NARROW** |
| `required_heading_levels` | which heading levels must appear | Yes | `h1,h2` | spec | **SURVIVE** |
| `require_faq` | FAQ-section-required check (toggle) | Yes | `true` | behavioural (format spec) | **SURVIVE** |

- The marker-leak and duplicated-token checks are the **model pattern**: they
  force-fail `qa_pass` *outside* the score ratio precisely so no threshold can dilute
  them (the code says so: folding them into the denominator "would dilute the
  denominator and silently loosen every threshold-tuned template"). This is verdict
  logic done right — already locked, no knob.
- **The four structural numerics → NARROW.** These are the clearest *legitimate*
  per-template variance in the whole set: a news blurb, a pillar page and a company
  profile have genuinely different length/section specs. They already carry sane
  `min`/`max` bounds in the manifest and a weakened value is named in the `violations`
  trace. Keep tunable — but the rule requires the reason be **written down** (one line
  per template: "company-profile spec = 8 sections / 2000 words"). Undocumented ⇒
  lock to default.
- **`required_heading_levels` / `require_faq` → SURVIVE.** These declare *what this
  content format is*, not *whether the checker worked*. Not every format has an FAQ or
  an H1+H2 spine; turning `require_faq` off is an honest format statement, recorded in
  `checks_total` / `violations`, and the checker still grades everything else. They do
  not certify unverified content. (Caveat: `require_faq` toggling changes the score
  denominator — if it is ever abused to inflate a pass, move it to a force-fail like
  the marker checks. Not needed today.)

### 3.4 loop-router (`step-7-routing/loop-router`)

| Knob | Controls decision via | Template-set? | Default | Kind | Verdict |
|---|---|---|---|---|---|
| `route()` priority chain | the entire routing verdict | **No** — hardcoded | — | verdict logic | **LOCKED ✓** |
| `expected_checks` | which step-6 checkers MUST report (H23 guard) | Yes (multiselect) | all 5 | behavioural (verdict logic) | **LOCK — by deriving** |
| `default_no_qa` | no-QA-at-all ⇒ `approve` vs `flag_manual` | Yes | `flag_manual` | behavioural (verdict logic) | **LOCK** |
| `max_loops` | `loopCount >= max_loops` ⇒ terminal `failed` | Yes | `3` | numeric threshold | **NARROW** |
| `min_source_pages` | below ⇒ discovery-loop replaced by `flag_manual` | Yes | `8` | numeric threshold | **NARROW** |

- **`default_no_qa` → LOCK to `flag_manual`.** `approve` auto-approves an entity with
  **no QA at all** — a green with zero evidence, invisible. It is the sibling of H23.
  Never allow `approve`; hardcode `flag_manual`.
- **`expected_checks` → LOCK, by DERIVING it from the plan** (not hand-set, not
  template-narrowed). See §4 — the measurement forces this conclusion. `default 5`
  here means the list of all five checker keys (`keyword, meta, citation,
  hallucination, structural`), not a number; **narrowing the list re-opens exactly the
  H23 hole** it was filed to close (a checker dropped from the list is allowed to be
  missing again).
- **`max_loops` / `min_source_pages` → NARROW.** Numeric, bounded (`min`/`max` in the
  manifest), and they change the *route* (loop vs flag) not a pass→fail flip; a
  changed value is recorded. Keep tunable with a written reason; neither can
  manufacture a false green.

### Recommendation: DERIVE, do not hand-set and do not per-template-narrow

The prompt's two candidate fixes are *narrow `expected_checks` per template* or
*derive the expected set from the template's own configured checkers*. Derive:

- **Hand-set `default 5` is already wrong for the fleet** (9/13 router templates).
- **Per-template narrowing rots.** It puts the truth in two places — the plan (which
  checkers run) and the router option (which are expected) — that must be kept in
  sync by hand for every template and every plan edit. The H23 bug is itself a symptom
  of the router not knowing what the plan scheduled; a hand-maintained list re-creates
  that gap. And a template-editable opt-out list is a **weakening vector** (§3.4:
  narrowing it re-opens H23).
- **Derive = single source of truth.** The real invariant is: *every checker the plan
  actually scheduled in step 6 must produce a verdict.* A checker that was never
  scheduled is not "missing," it is "not part of this template's QA"; a scheduled
  checker with no verdict is the crash/skip H23 exists to catch. Deriving the expected
  set from the scheduled step-6 QA submodules captures exactly that distinction, with
  no knob to weaken.
- **Where it lives:** loop-router today sees only the entity item pool, not the plan.
  The derivation belongs in the plan-aware engine layer (`content-pipeline-v2`):
  compute the expected set from the plan's scheduled step-6 QA cards and inject it as
  the run option (replacing the all-5 default). The module stays generic; the option
  becomes engine-computed, not template-authored. **This is a skeleton change, not a
  modules-only change — and it gates the merge.**

**Do not merge `qa-quartet-modules` until the expected set is derived** (or, as a
stopgap only, until every router template's `expected_checks` is explicitly set to
its scheduled subset). Merging as-is flags every entity on the production template.

### QA strictness governance (W2.3a + W2.3b)

The step-6 QA checkers and the step-7 loop-router enforce one fixed contract:
**a template cannot rewrite what a green QA verdict means.** Prompts and verdict
logic are code-locked and ignore any template override:

- **hallucination-detector** — the fact-check prompt (W2.3), `no_sources_behavior`,
  and `allow_empty_content` are locked to fail-closed. No sources, or no content,
  always fails; a pipeline that legitimately lacks them omits the checker in its plan
  rather than softening the verdict.
- **citation-coverage-checker** — `require_at_least_one_citation` and
  `require_factual_citations` are locked on. A template cannot switch the citation
  requirement off.
- **qa-structural** — the taxonomy-marker and duplicated-token checks force-fail
  outside the score ratio and cannot be tuned away.
- **loop-router** — the routing priority chain is hardcoded; `default_no_qa` is
  locked to `flag_manual` (no QA never auto-approves); the expected-checker set is
  **derived from the checkers each template's own execution plan schedules**, not a
  template-authored option.

Templates MAY tune the following **numeric thresholds / format specs**, because a
weakened threshold is recorded in the run and leaves a trace (rewritten verdict logic
would not). Each override MUST carry a one-line rationale where the template sets it;
an undocumented override is treated as a bug:

- hallucination-detector: `pass_threshold` (floored), `flag_zero_claims_over_chars`
  (calibration — measure the trip rate, do not dial it down to silence a genuine
  halt), `max_source_chars`, `claims_per_batch`.
- citation-coverage-checker: `pass_threshold` (floored); `verify_urls` (report-only).
- qa-structural: `pass_threshold` (floored), `min_sections`, `min_words_per_section`,
  `min_total_words`, `required_heading_levels`, `require_faq` — the content-format
  spec, which legitimately varies per template.
- loop-router: `max_loops`, `min_source_pages`.

## 6. Open defect (Task 4) — meta-compliance-checker grades the wrong draft

**Not fixed here. Recorded to write a unit from.** Class: **H18b** (grade the draft
step-8 publishes). Scoped out of the quartet's H18b fix
(`docs/evidence/phase1-qa-quartet/README.md` §H18b, "Scoped out — meta-compliance-checker").

**Where.** `modules/step-6-qa/meta-compliance-checker/execute.js:207-221`.

**Root cause.** The three content checkers fixed in H18b select the single latest
draft (`contentItems.at(-1).content_markdown`) — the exact draft step-8 publishes
(`markdown-output:189` / `html-output:182` / `json-output:151` all use
`.filter(i => i.content_markdown).at(-1)`). `meta-compliance-checker` does **not**.
It resolves meta with a **first-match priority chain** across *all* generated drafts:

```js
// Priority 1 (execute.js:207-211)
for (const item of contentItems) {
  if (!item.content_markdown) continue;
  if (item.meta_title && !metaTitle) metaTitle = item.meta_title;          // FIRST wins
  if (item.meta_description && !metaDescription) metaDescription = item.meta_description;
}
// Priority 2 (execute.js:214-222): same first-match over frontmatter
```

content-writer and tone-seo-editor both emit `content_markdown` under `add`, so both
drafts survive the pool in insertion order `[content-writer, tone-seo-editor]`. The
`!metaTitle` guard stops at the **first** generated draft — content-writer's — while
step-8 publishes tone-seo-editor's `.at(-1)`. When tone-seo-editor changes the meta
(tightens an over-length title, rewrites the description), the checker grades meta
that was **never published**. The run `cb49ef80` fix (`if (!item.content_markdown)
continue;`) fixed the *scraped-vs-generated* confusion — a different, earlier bug — but
left the *first-vs-latest generated* selection untouched.

**Failure scenario (false green — the dangerous direction).** Pool: item A
(content-writer) `meta_title` = a clean 58-char title; item B (tone-seo-editor)
`meta_title` = the refined title but now ending `…` (truncation) or pushed to 66
chars. Checker reads A (first-match) → Check 1/Check 6 **pass** → `qa_pass:true`.
Step-8 publishes B → a truncated/over-length title ships under a green meta verdict.

**Failure scenario (false red).** A = over-length 66-char title (would fail Check 1);
B = tone-seo-editor's corrected 58-char title. Checker grades A → **fails** a title
that was fixed and never shipped → spurious `loop_generation`.

**Fix direction (do not implement here).** Mirror H18b: resolve Priority-1/Priority-2
meta from the **latest** content_markdown draft only —
`const latest = contentItems.filter(i => i.content_markdown).at(-1)` — then read
`latest.meta_title` / `latest.meta_description` / its frontmatter, before the
seo-plan (Priority 3) and H1/first-paragraph (Priority 4) fallbacks. Carries the same
documented `.at(-1)` pool-order caveat as the other three (README §H18b "Caveat").

**Unit to write** (`meta-compliance-checker/test-latest-draft.js`, plain Node):
two-generated-draft entity, A-good/B-bad ⇒ expect FAIL (grades B); A-bad/B-good ⇒
expect PASS (grades B); single-draft entity unchanged. RED on current first-match,
GREEN after `.at(-1)`.

**No BACKLOG number claimed.** Per `BACKLOG.md`'s number-allocation rule, an item
number is allocated only by editing `BACKLOG.md` in a pushed commit — never in a
report first. File it there before citing it by number.
